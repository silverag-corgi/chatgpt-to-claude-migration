# 新しいエクスポートで解析する実行手順

2026-11-07時点。現在の解析結果を保管し、新しいエクスポートを別の作業フォルダで解析するための手順。

## 目的に応じた手順

| 目的                                           | 手順                                                                                                                                          |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| OCRの中断後の再開・負荷調整・進捗やログの確認  | 必要時に [OCRの運用・トラブル対応](OCR-OPERATIONS.md) を参照。対象の作業フォルダで操作する                                                    |
| 保存済みの確認・採否判断からMarkdownを再生成   | 対象の作業フォルダで `python3 scripts/build.py` を実行。会話を読み直したり、新しい情報を抽出したりする処理ではない                            |
| 同じ入力でREADMEの抽出・分類条件を変更して解析 | 原本・中間データの一致を検証し、変更条件に関係する原文と既存の採用判断を再評価してから生成する。`build.py` だけでは意味内容の見直しは行わない |
| 新しくエクスポートしたデータを解析             | 以下の手順。入力・中間判断・OCR結果を新規作成                                                                                                 |

**現在は新しいZIPを差し替えるだけで全解析を自動実行できる構成ではない。**
スクリプトは正規化・OCR・検証・文書生成を補助する。会話と添付の意味解釈、事実の採否、重複統合はAIまたは人による確認が必要。
今回専用の判断・件数・画像番号もコードに残っており、新入力に合わせた修正が必要になる。

## 1. 新しい作業フォルダを作る

現在のフォルダは今回の入力・出力・判断記録を含めて保管する。原本を置換・削除せず、新しい空のフォルダを用意する。
新フォルダへ `README.md`、`scripts/`、`docs/` を実ファイルとしてコピーする。スクリプトは自身の実体パスから作業ルートを決めるため、`scripts/` を旧フォルダへのシンボリックリンクにしない。

新フォルダの配置:

```text
新しい作業フォルダ/
  README.md
  scripts/
  docs/
  ChatGPT.zip       ← 新しいエクスポートZIPをこの名前で保存
  input/            ← そのZIPだけを展開
  output/           ← 解析時に新規作成
```

旧 `input/` に追加展開しない。旧 `output/` も新フォルダへコピーしない。
新ZIPの会話JSONが `input/conversations*.json` に直接配置されるよう、展開後の階層を確認する。
現行 `prepare.py` はZIPの自動展開を行わない。また `conversation_asset_file_names.json` を読み込むため、エクスポート形式が変わった場合は読み込み処理の対応が必要。

## 2. 実行環境を用意する

同じPCでは、現在の `.venv-ocr/`、`.venv-ndlocr/`、`.ocr-tools/`、`.ocr-cache/` を再利用できる。
これら4ディレクトリを新フォルダから旧環境へリンクする方法もある。旧フォルダを移動・削除せず、同時に両方のOCRを実行しない。排他ロックは作業フォルダごとで、別フォルダ間の同時実行は防げない。

Python仮想環境は移動・コピーすると元の絶対パスが残ることがあるため、別PCでは再構築する。環境情報は旧 `output/intermediate/image-ocr/{paddle,ndl}/environment.json` に記録されている。新規構築時のパッケージ・モデル取得は別途必要。

今回の採用設定は **PP-OCRv5_mobile_det + PP-OCRv5_server_rec、文字認識バッチ6**。
負荷対策ではまず並列数を下げ、モデル・画像サイズ・認識バッチを無断変更しない。

## 3. 正規化と、新入力に合わせた確認

以下はすべて新フォルダの直下で実行する。

```sh
python3 scripts/prepare.py
```

`output/intermediate/inventory.json` のZIP照合・会話件数・重複・構造上の問題を確認する。
`prepare.py` は初回の入力台帳作成用。同じ解析の途中で繰り返して不変性の基準を更新しない。

会話本文を分割して確認する例（終了番号は含まない）:

```sh
python3 scripts/review.py 0 10 --full
```

会話・添付を確認し、新しい `entries.psv` と `consolidations.json` を作る。これらを作成する自動抽出コマンドは現在ない。
PSVの各行は `テーマ|カテゴリ|出典参照（カンマ区切り）|本文`。
出力カテゴリは `指示・基本情報・経歴・プロジェクト・好み`。以前の途中稿の英語カテゴリは生成時に日本語へ変換する。
統合判断JSONは `build.py` の `make_entries()` が読み込む形式に従う。
旧ファイルの `CxxxxUxxx` や行番号をそのまま移植しない。会話番号・画像番号は並び順に依存しており、新エクスポートで変わり得る。
同じ入力でREADMEだけを変更した場合は、既存のハッシュ台帳を保持し、原本・正規化データ・OCR結果の一致を確認して再利用できる。`prepare.py` やOCRを無条件に再実行せず、抽出・分類・要約の判断を更新する。
差分確認には会話ID・メッセージID・添付SHA-256を使う。現行コードに差分解析・OCRキャッシュ移植の自動機能はない。

実行前に、少なくとも次の今回専用処理を新入力へ合わせる:

- `build.py`: 長文の会話参照集合、添付名別の確認済み扱い、今回固有の報告文・日付。会話件数は現在、入力台帳から検証する。実際に確認する前に「確認済み」にしない。
- `ocr_images.py`・`run_ocr_low_memory.py`・`summarize_ocr.py`: `img-143` の強制補完・回転処理。同じ番号でも新入力では別画像になり得る。新画像とハッシュで対象を決め直す。
- `ocr_images.py`: 直接実行時の画像終了番号の既定値230。新しい画像総数を明示する。
- `summarize_ocr.py`: 今回の230点・採用例・退避履歴などの固定説明。
- `verify_unified_ocr.py`: 今回の旧モデル再処理・削除証跡を検証する専用ツール。新解析の一般検証としてそのまま使わない。

`build.py` の添付整理処理は `assets-reviewed.json` を生成するが、既存の判断に基づく処理も含む。上記を修正し、新しい会話・添付の対応と実際の確認状態を整理してから使用する。

## 4. 画像をOCRする

新しい `assets-reviewed.json` と原本ハッシュ台帳が揃ってから、画像一覧を生成する（この呼び出しはOCRモデルを読み込まない）:

```sh
.venv-ocr/bin/python -c 'import sys; sys.path.insert(0, "scripts"); from ocr_images import manifest; print(len(manifest()))'
```

続いて一次OCRだけを実行する:

```sh
python3 scripts/run_ocr_low_memory.py --status
python3 scripts/run_ocr_low_memory.py --primary-only
```

一次結果・対象画像を確認してから、補完を実行する:

```sh
python3 scripts/run_ocr_low_memory.py
```

既定はPaddleOCR最大2ワーカー・各CPU4スレッド、空きメモリ2GiB未満で停止。負荷を下げる場合は `--workers 1` を追加する。
`--batch-size` はプロセスを再起動するまでの画像数であり、文字認識バッチ6とは別設定。
中断時は同じコマンドで続行する。詳細は [OCR-OPERATIONS.md](OCR-OPERATIONS.md)。

## 5. 内容確認・統合・検証

OCR結果は自動で本人情報として採用しない。原画像と発言文脈を照合し、`image-ocr/review-decisions.json` を新規作成して、一次・補完の確認状況、採否、理由、関連エントリを記録する。
`review_ocr.py` は分割表示を助けるが、確認済みフラグを自動で付けるものではない。
数値や型番の補足は `entries.psv`／`consolidations.json` の新しい出典へ反映する。

```sh
python3 scripts/summarize_ocr.py
python3 scripts/build.py
python3 scripts/build.py --verify-only
```

確認先:

- `output/reports/validation.json`: 最終検証。全項目PASSを確認。
- `output/reports/image-ocr/validation.json`: 原本ハッシュ、一次・補完、内容確認記録。
- `output/reports/extraction-report.md`: 対象範囲、未解析・欠落資料、採否方針。
- `output/import/complete-import.md` とテーマ別12ファイル: 最終成果物。

元ZIPがない場合、ZIPとの照合は成功扱いにせず、`validation.json` の `skipped_checks` に理由を記録する。入力原本とのSHA-256照合は引き続き必須。空の `input/.gitkeep` は管理用ファイルとして原本件数から除外する。
今回の日本語プロンプト対応で作った `japanese-prompt-review.json` は、同じ入力での再生成・検証に必要な再評価記録。新しいエクスポートには流用せず、対応する確認記録を新規作成する。

前回比の追加・訂正・削除も確認する。件数が前回と一致する必要はない。
Claudeへの投入は別の操作。このスクリプト群は実際のインポートを実行しない。

## AIへ解析を依頼する例

> エクスポートデータを配置しました。
> README.mdとdocs/HOW-TO-RUN.mdに従い、新入力に必要なスクリプトの修正から内容確認・生成・検証まで実行してください。
> 旧結果の出典番号や確認済みフラグは流用せず、今回のmobile検出・server認識、文字認識バッチ6を維持してください。
> メモリ監視と中断後の再開を有効にし、画像は外部へ送信しないでください。
